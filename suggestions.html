Review worksheet

Six questions to answer before choosing. They are policy choices, so they carry no source link — they are the reviewer's input, not an observation.

1. What is the decision for?

  • Publish a trustworthy research record (→ Path A)
  • Find a testable edge (→ Path B)
  • Answer the availability question (→ Path C)
  • Pay a winner (→ Path D, blocked)

2. What budget is available for data?

  • None (Path A only)
  • A single price-feed licence (Path B)
  • Price feed plus depth/participation data (B + C)

3. What is the time horizon?

  • This week: policy and presentation only
  • This season: pre-registered prospective test
  • Multi-season: proper replication before any verdict

4. What will you do if nothing validates?

  • Publish the negative result and stop (defensible)
  • Keep searching — then log every trial (S13) or the correction becomes fiction

5. Who owns the decision and its reversal condition?

  • Name one owner, one date and one condition that would reverse the choice (S22)

6. Which single question, if answered, would change the most?

  • Q09: authenticated prices. It gates every ROI, every gate and every reward.

Change-control workflow

  1. 1. Read — questions.html — check what is answered and what is blocked.
  2. 2. Choose — Pick a path above (A/B/C/D) or a subset of suggestions.
  3. 3. Record — Write the decision, owner, date and reversal condition into DECISIONS.md (S22), linked below.
  4. 4. Claim — Add the task and file scope to COORDINATION.md before touching code.
  5. 5. Implement — Only the claimed scope; every new table row needs an official/primary reference.
  6. 6. Verify — `make build` and `make test`; the verify workflow must pass before merge.
  7. 7. Publish — Merge to `main`; GitHub Pages redeploys from the repository root.
  8. 8. Review — Re-open this page: a suggestion that shipped moves to Delivered, with its test.

Review rule

  1. Enter the suggestion with ID, description, expected decision impact and source.
  2. It moves to “Under review” when a reviewer picks it up.
  3. Record the decision: adopt, adopt with modification, or reject — with rationale and a source link.
  4. Adopted changes are implemented in code, verified (make build && make test), and only then published.
  5. Rejected or deferred suggestions stay visible with their rationale; nothing is silently dropped.
